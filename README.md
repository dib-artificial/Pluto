> [!WARNING]
> **Bluetooth Configuration and Flash Memory Optimization**
>
>If you have watched the video above, you might have noticed that an external Bluetooth module (HC-06) is used, even though the ESP32 module comes with built-in Bluetooth.
>
> This approach was taken to conserve the ESP32's flash memory and RAM. Using the built-in Bluetooth would consume a significant amount of these resources, leading to a memory shortage for the 'Pluto Engine.' Consequently, a separate Bluetooth module was used instead.
>
> The HC-06 communicates with the ESP32 through UART2 using the following configuration:
>
> ```cpp
> #define RX2_PIN 16
> #define TX2_PIN 17
>
> Serial.begin(115200);
> Serial2.begin(9600, SERIAL_8N1, RX2_PIN, TX2_PIN);
> ```
>
> **Code explanation:**
>
> - `RX2_PIN 16`: ESP32 GPIO 16 receives serial data.
> - `TX2_PIN 17`: ESP32 GPIO 17 transmits serial data.
> - `Serial.begin(115200)`: Initializes the USB serial interface for debugging.
> - `Serial2.begin(9600, SERIAL_8N1, RX2_PIN, TX2_PIN)`: Initializes UART2 at 9600 baud with 8 data bits, no parity, and 1 stop bit.
>
> **Note:** These are UART pin definitions and serial initialization settings, not timer configurations.

## Flutter Bluetooth Application

A lightweight Flutter chat application is used to communicate with the 'Pluto' engine on an ESP32. User-entered text is sent to an HC-06 Bluetooth module, while text generated by the Pluto engine is received back in the Flutter app. Only the phone's Bluetooth functionality is utilized for this process.

The application performs three primary functions:

1. **Bengali-to-English Translation:** Bengali or another language is taken as input, and then that text is converted into English via the internet.
2. **Transmission:** The translated text is then sent to the HC-06 module from the phone via Bluetooth. (Pluto Engine) supports only the English language.
3. **Text Reception:** The text generated via feedback from the system (Pluto Engine) is received in the Flutter app through an HC-06 Bluetooth module.

The Bluetooth connection between the phone and the ESP32 does not itself require an internet connection. However, the translation feature requires internet access.

## I²C Sensor Detection Benchmark: ESP32 vs Pluto - TinyML AI

This benchmark compares a conventional ESP32 I²C address scan with Pluto processing a natural-language instruction to identify connected I²C sensors.

### Test Instruction

```text
Check how many sensors are connected to I2C SDA GPIO 21 and GPIO 22 (SDA - SCL)
```

**Pluto's response:**

```text
One address is found here (0x76)
```

The detected I²C address was `0x76`.

### Benchmark Results

| Metric | ESP32 Pure I²C Scan | Pluto Engine |
|---|---:|---:|
| Execution scope | Direct I²C address scanning | Natural-language processing and task execution |
| SDA pin | GPIO 21 | GPIO 21 |
| SCL pin | GPIO 22 | GPIO 22 |
| I²C clock | 100 kHz | 100 kHz |
| Addresses checked | 1–126 | Determined by Pluto's implementation |
| Devices detected | 1 | 1 address reported |
| Average execution time* | ~18.801 ms | ~110.133 ms |
| Relative execution time | 1× | ~5.86× |

\* An average value is presented here for the ESP32; during testing, the same command was checked 50 to 100 times.

### Understanding the Difference

In this context, the ESP32 I²C scanner directly checks the addresses of connected devices or sensors to determine which ones are responding.

An important point to note here is that the Pluto engine performs several preliminary tasks—such as interpreting language commands, establishing internal structures, and generating instructions for the control layer—before proceeding.

Naturally, the Pluto engine’s operation involves more overhead compared to a direct I²C scan. However, this does not imply that the Pluto engine is five times slower. Furthermore, these figures are not definitive, as the time required depends on various factors, such as the complexity of the tasks being executed and the processor speed.

### Pluto Benchmark Code

The following code measures the elapsed time of each Pluto function call over 50 iterations.

```cpp
for (int i = 0; i < 50; i++) {

    int64_t startTime = esp_timer_get_time();

    pluto("Check how many sensors are connected to I2C SDA GPIO 21 and GPIO 22 (SDA - SCL)");

    int64_t endTime = esp_timer_get_time();

    int64_t elapsedUs = endTime - startTime;

    Serial.printf(
      "Test %03d | %lld us | %.3f ms\n",
      i,
      (long long)elapsedUs,
      elapsedUs / 1000.0
    );
}
```

The measured time shown here begins before the main function is called and ends only after the main function has finished its execution.

This has been done solely for testing purposes; the recorded time includes not only the duration taken by the Pluto engine but also the overhead associated with the underlying hardware.

### Important Warnings and Limitations

**1. Different benchmark scopes**

A standard ESP32 scanner measures the process of directly scanning for I²C addresses, whereas the Pluto engine performs additional tasks, such as text processing and managing the control layer. While these metrics are useful for understanding end-to-end latency, they do not provide a direct comparison of the hardware-level scanning performance between the two systems. For a better understanding, please refer to the architecture diagram below.

**2. Results depend on configuration**

Execution time may vary based on factors such as the ESP32 board, Arduino core version, compiler optimizations, I²C clock frequency, active control functions, and the number of addresses or devices being tested. In short, hardware specifications play a significant role here.

**3. RAM usage is not reported in this benchmark**

This benchmark only estimates the Pluto Engine processing time; it does not provide data regarding RAM usage. This is because the model retains certain information—such as task/layer details and historical runtime data—which makes it impossible to directly determine the exact amount of RAM consumed while the Pluto Engine is running.

Assessing memory usage would require a separate memory benchmark. Such metrics should be measured and reported independently of execution time.

**4. Results are specific to the tested configuration**

The values ​​mentioned here describe the results of the provided ESP32 tests and the Pluto configuration. These should not be considered as performance benchmarks applicable to other supported microcontrollers or different versions of Pluto.

### Conclusion

In the examples provided above, a standard ESP32 I²C scan took approximately 18.8 milliseconds to complete, whereas the entire instruction-processing workflow of Pluto required about 110.1 milliseconds.

This additional time reflects the scope of the Pluto engine's operational processing. Therefore, this duration should be evaluated in the context of Pluto’s hardware-control capabilities, memory requirements, and the complexity of the instructions.

### Why is this model named "Pluto"?

> It’s quite simple: on August 24, 2006, Pluto was removed from the list of planets. Since then, it has been all but forgotten, which is why I’ve named this (TinyML AI) project "Pluto," so that the name might be heard once again.

---

**1. Sentence Filter Layer:**
The Pluto Engine is written entirely in pure C++. User-input text first enters the "Sentence Filter Layer," which determines the maximum number of words that can be processed at once. This limit is configured based on the specific microchip—its processor, ROM, and RAM capacity—as well as the features supported by the hardware on which the Pluto Engine is running.

The Pluto Engine has been implemented on platforms including Arduino Mega, STM32, the ESP32 series, and Raspberry Pi Pico W.

**2. Text Section Layer:**
In this layer, the text is assigned a specific, compact ID.

**3. GPIO Layer:**
This layer handles alerts and buzzer functions. It defines the operational scope; for instance, if PWM (Pulse Width Modulation) is integrated, the system generates a detailed, numerical "hidden layer" specifying how to produce the PWM signal, the required number of cycles, and the supported GPIO pins. This data is then fed into the Pluto Engine.

**4. Main Engine:**
The core Pluto Engine operates through various hidden layers or sections. It employs multiple "emotion sections" to emulate human mechanisms—though this does not mean the engine actually possesses or retains emotions. The Pluto Engine’s architecture differs significantly from conventional models, as it is designed to mirror human cognitive mechanisms through a variety of distinct functional sections.

**5. Generative Section:**
This section does more than just generate content; it aggregates data from various other sections to produce two distinct final outputs: the generated text and the instruction data for the hardware control section.

---

**6. Hardware Control (Tree) Layer:**
A visual representation of this layer is provided below. The final instructions generated by the Pluto Engine consist of three key components:

**A:** This (Tree) layer begins with an address—or, depending on requirements, multiple addresses—where each address carries distinct information.

**B:** Next is the "Instruction GPIO" section, which contains data specifying the function of each GPIO pin.

**C:** FIET (Feedback Instruction Engine - Thinking): This is a critical component of this layer. There can be multiple instances of FIET. Its function is to provide feedback on how GPIO pins are being utilized (as inputs or outputs) and to notify the Pluto Engine about ongoing tasks. Furthermore, it receives instructions from the Pluto Engine and implements necessary adjustments within the Hardware Control (Tree) Layer. This process is distinct from the Pluto Engine’s initial instruction generation; it functions much like the mental deliberation a human undergoes before taking an action—the Pluto Engine performs this "thinking" process, and the resulting information is transmitted via FIET.

*Decoding within this layer occurs internally. When the CPU is in operation, it interacts exclusively with the Hardware Control (Tree) Layer, effectively bypassing the processing stages of the Pluto Engine. The various processing layers are only activated when new instructions are received from the user, which significantly enhances the CPU's performance.*

## 03 — Training & Limitations (How this model is trained)

A distinct approach is employed for training the Pluto Engine. It utilizes a custom C++ architecture—centered around a "master" Pluto Engine—that is tailored to the specific capabilities and features of various microchips. Rather than relying on parameter- or pattern-based learning, it mimics the human learning process.

During the model training phase, the system is trained using a variety of input-output features and their associated details. Based on this data, it automatically generates hidden layers—incorporating specific features—which are then integrated into the Pluto Engine designed for the respective microchip.
